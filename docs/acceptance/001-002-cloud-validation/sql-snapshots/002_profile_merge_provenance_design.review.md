# 002 游客档案合并资格与字段来源方案（已审核）

## 1. 状态

本文是 002 身份合并设计的已审核补充方案，已于 2026-08-18 确认设计决策，进入 002a–002d 修订与逐份静态审核。

- 不修改已部署的 001 基线。
- 002a–002d 按本文修订，但仍必须从 002a 开始逐份静态审核；未审核通过前不部署。
- 本变更只影响游客普通档案的合并资格；不改变事件迁移、经期历史重新授权、幂等或原子回滚设计。
- 身材目标“3 天窗口与严格度判断”仍是对话层待办，不在本方案实现。

## 2. 问题

`app.user_profiles` 保存当前普通档案快照，可能混合两类数据：

1. 普通问答中顺带提到的身高、体重、目标或饮食习惯。
2. 用户明确选择长期服务后，在长期建档流程中提供并确认的字段。

合并时只能信任第 2 类。现有快照和修订历史不能稳定证明每个字段的采集上下文。

## 3. 不采用整行布尔标记

不在 `app.user_profiles` 上增加类似 `is_long_term_profile` 的整行标记。

原因：同一行可能同时包含“长期建档中确认的身高”和“普通问答中提到的目标体重”。整行标记一旦为真，会错误提升其他字段的可信等级。

## 4. 建议新表：`app.long_term_profile_field_confirmations`

该表是追加式的字段确认事实，不替代 `app.user_profiles` 当前快照。

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `confirmation_id` | `uuid` | 主键 |
| `user_id` | `varchar(128)` | 所属用户 |
| `field_path` | `varchar(100)` | 规范路径，例如 `body.heightCm` |
| `confirmed_value` | `jsonb` | 本次确认后的规范值 |
| `profile_revision_id` | `uuid` | 对应的普通档案修订 |
| `onboarding_session_id` | `varchar(128)` | 后端生成的长期建档会话标识 |
| `confirmed_at` | `timestamptz` | 业务确认时间 |
| `created_at` | `timestamptz` | 数据库入库时间 |

约束：

- `field_path` 只允许 002 普通档案白名单中的 14 个字段。
- `confirmed_value` 不允许 SQL `NULL` 或 JSON `null`；清空字段不是可用合并值。
- `(user_id, field_path, profile_revision_id)` 唯一，防止同一修订重复写入确认事实。
- 为 `app.profile_revisions` 增加 `(user_id, revision_id)` 唯一键，新表使用 `(user_id, profile_revision_id)` 复合外键。这样由数据库保证修订必须属于同一用户，不只依赖 RPC 检查。
- 表只记录已确认字段，不用“整行已进入长期建档”代替字段证据。

建议索引：

```text
(user_id, field_path, created_at DESC, confirmation_id DESC)
```

合并 RPC 使用数据库生成的 `created_at` 和 `confirmation_id` 取每个字段的最新合格确认值，不使用可能受业务时钟影响的 `confirmed_at` 决定先后顺序。

## 5. 写入边界

### 5.1 普通问答

- 可继续更新 `app.user_profiles`，供当前会话和基础档案使用。
- 不得写入 `app.long_term_profile_field_confirmations`。
- 因此这些值不参与注册后的游客档案合并。

### 5.2 长期建档

只有同时满足以下条件才写字段确认事实：

1. 用户已明确选择长期建档路径。
2. 字段在该建档路径中由用户明确提供或复核。
3. 字段值已通过现有契约校验。
4. `user_profiles` 更新、`profile_revisions` 追加和字段确认追加在同一数据库事务中成功。

“进入长期建档”本身不会自动把旧 `user_profiles` 整行标记为可合并。如果建档流程要复用用户之前说过的值，必须在建档上下文内将它明确展示或复核，然后产生新的字段确认事实。

### 5.3 不信任客户端标记

客户端不能直接传入 `isLongTermOnboarding=true` 或任意指定可合并字段。字段确认必须由受信后端根据已确认的 LangGraph/服务状态生成，并通过受控 RPC 写入。

在数据库能够验证长期服务状态之前，该 RPC 只能作为后端内部边界，不得暴露为可由前端自由组装参数的公共接口。

## 6. 修订后的档案合并规则

对游客普通档案的每个白名单字段分别执行：

1. 查找该游客、该 `field_path` 的最新长期建档确认事实。
2. 不存在时：该游客字段在合并中视为不存在；不填补，不比较，不生成冲突。
3. 存在时：以确认事实的 `confirmed_value` 作为游客合并值，不盲信 `user_profiles` 当前行中可能被普通问答后续覆盖的值。
4. 账号值空缺：用游客合格确认值填补。
5. 账号值与游客合格确认值相同：保留，不生成冲突。
6. 账号值非空且不同：账号优先，写入 `profile_merge_conflicts.pending`。

如果游客没有任何合格字段：

- 不调用档案保存 RPC。
- 不产生档案修订。
- 不产生档案冲突。
- 注册后由对话层重新开始基础信息采集。

## 7. 与冲突裁决闭环的关系

冲突仍按字段粒度记录。本方案只在冲突比较前新增“游客字段是否具备合并资格”的前置过滤。

`profile_merge_conflicts` 未实现裁决 RPC/UI/积压告警的已知缺口保持不变，不因本方案被视为已解决。

## 8. 对 002a–002d 的预期改动

### 002a

- 新增 `app.long_term_profile_field_confirmations` 及约束、外键和索引。
- 为 `app.profile_revisions` 补充 `(user_id, revision_id)` 唯一键，支持新表的同用户复合外键。
- 不给 `app.user_profiles` 增加整行可合并布尔标记。

### 002b

- 新表启用 RLS。
- `PUBLIC` 和 `diet_app` 不获得新表直接写入权限。
- 需要时只通过归属校验的受控 RPC 读写。

### 002c

- 增加长期建档字段确认的原子写入边界，或扩展现有档案保存 RPC，使档案修订与确认事实不会部分成功。
- 合并 RPC 不再从游客 `user_profiles` 整行取值；只取每个字段最新的合格确认值。

### 002d

新增至少以下真实行为测试：

1. 游客只有普通问答档案：零填补、零冲突。
2. 游客只完成部分长期建档字段：只合并该部分字段。
3. 普通问答值与长期建档值混合：只采用后者。
4. 进入建档但没有确认某字段：该字段不参与比较。
5. 同一字段有多次长期建档确认：使用最新合格值。
6. 伪造字段路径、跨用户修订或重复确认：数据库拒绝。
7. 档案保存后、确认事实写入前注入故障：档案和修订一起回滚。

## 9. 已确认决策

1. 使用追加式字段确认事实表，不使用 `user_profiles` 整行布尔标记。
2. 之前的值可在长期建档中重新获得合并资格，但必须由秘书主动把该值重新摆出、用户正面回应确认。后台静默复用旧值不得生成确认事实。该标准与未来目标体重改动时的“秘书专门问过、用户正面回答”保持同一严格尺度。
3. `onboarding_session_id` 作为必填审计键，由后端生成，不暴露给模型。
4. 修订 002 主设计和 002a–002d 后，从 002a 重新开始逐份静态审核。
