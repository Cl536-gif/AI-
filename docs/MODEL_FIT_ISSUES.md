## 已处理

### FIT-001 — 采集回复出现句首孤立冒号

- 日期：2026-08-31
- 状态：已关闭
- 测试场景：企业微信真实路径 `食堂 → 自选 → 辣 → 30 → 羊肉 → 上镜`。
- 实际行为：回答“羊肉”后，回复以无语义的 `：` 开头。
- 期望行为：用户可见回复及写入对话历史的内容都不能以孤立中英文冒号开头。
- 归因：LangGraph `askNextQuestion` 的模型生成结果缺少句首孤立标点清理，不是前端渲染问题。
- 风险分析：低风险；只处理回复开头的连续中英文冒号，不改正常句内标点。
- 用户批准记录：2026-08-31，批准立即修复并加入真实路径多次回归。
- 修改记录：模型回复进入校验和对话历史前，确定性清理句首孤立 `：` / `:`。
- 验证结果：确定性坏样本测试通过；完整真实路径使用3个全新测试身份连续运行3次，全部无句首孤立冒号。

### FIT-002 — 状态未完成却重复播报“最后一个问题”

- 日期：2026-08-31
- 状态：已关闭
- 测试场景：企业微信真实路径 `食堂 → 自选 → 辣 → 30 → 羊肉 → 上镜`。
- 实际行为：预算后仍缺忌口、目标和运动，却说“还差最后一个小问题”；忌口后仍缺目标和运动，又说“最后想问问你”。
- 期望行为：剩余两项或更多时，不能出现“最后”或“还/只差一个”的进度播报；真正只剩一项时不误伤。
- 归因：系统提示词虽已禁止错误报数，但 `askNextQuestion` 没有用真实槽位状态做确定性校验。
- 风险分析：低风险；不改变提问顺序或完整性规则，只拦截与状态矛盾的话术并触发现有重试/兜底。
- 用户批准记录：2026-08-31，批准按状态确定性拦截，不依赖提示词。
- 修改记录：根据六项槽位及食堂额外打饭方式计算实际剩余项；剩余超过一项时拦截所有含“最后”或“还/只差一个”的进度话术。同步移除节点任务说明中容易诱导模型误解的“还差某一项”表达。
- 验证结果：原始两个坏样本、真实回放新出现的“那最后再确认一个”变体及真正只剩运动一项的边界测试全部通过；完整真实路径重新连续运行3次，全部通过。

### FIT-003 — “最多采集3轮”与“全部信息确认后才出方案”冲突

- 日期：2026-08-31
- 状态：待批准
- 测试场景：新用户首次饮食信息采集，食堂场景可能需要连续回答7项信息。
- 实际行为：LangGraph 状态机要求全部必填项确认后才允许出方案，覆盖了提示词中“第3轮先给暂定方案”的要求，用户会连续多轮只回答问题。
- 期望行为：待产品决策；需要在早期价值反馈与方案信息完整度之间明确取舍。
- 影响与严重程度：中高；会影响首次接待时长、用户中途流失、方案安全性与准确度。
- 初步归因：LangGraph 路由规则与系统提示词的产品规则冲突。
- 风险分析：修改会改变方案触发时机和不完整资料的处理方式，不能作为低风险话术修复直接合入。
- 建议方案：候选方向为3轮内优先采集安全和可执行信息并给暂定方案，其余信息在方案后补充；是否接受资料不全导致的方案质量折损，等待产品负责人明确决定。
- 用户批准记录：2026-08-31，明确不批准现阶段修改核心流程逻辑。
- 修改记录：无。
- 验证结果：待产品决策后制定。

### SIM-001 — 静态示例对话绕过企业微信真实开场

- 日期：2026-08-31
- 状态：已关闭
- 测试场景：企业微信新用户首次进入模拟器。
- 实际行为：页面预置了公司就餐、口味、忌口和目标示例，看起来像 LangGraph 已经完成部分采集。
- 期望行为：保留企业微信外观，但沿用 `compare-v2.html` 右栏入口；用户首条消息直接进入 LangGraph，不预置消息、不经过渠道欢迎或服务选择。
- 归因：渠道模拟器初始化错误，不属于 LangGraph、知识库或提示词问题。
- 修改：删除静态消息和错误的企业微信中转入口；使用与 compare-v2 相同的持久化 `deviceId`，首条消息直接调用 `/api/chat-langgraph`，后续复用返回的 `threadId`。新建对话仅重置线程并存档，另设全新测试用户操作。
- 验证：首轮两段回复按2.5秒依次显示；第二轮沿用线程并确认场景槽位；新建对话清空消息并生成本地存档；浏览器无控制台错误。
