# LangGraph V3 实测待统一修改清单

> 本文件只记录实测发现，不代表已经修改。等本轮 LangGraph 人工测试结束后统一评审、统一实现，避免边测边改造成回归。

## 1. 食物与分量单位必须匹配

### 实测问题

方案中出现用“拳”描述水煮蛋等不适用食物的情况。模型不能把通用手掌估量单位机械套到所有食物上。

### 统一修改目标

- 米饭等主食：碗、拳、克。
- 馒头、花卷、鸡蛋、鸡腿、鸡翅：个或只；必要时补充大小。
- 蔬菜：份、掌或拳。
- 豆腐：块或份。
- 牛奶、豆浆等液体：毫升或杯。
- 坚果：克或小把。
- 建立食物类别与允许单位的映射，并在方案输出后检查；发现“半拳鸡蛋”“一掌鸡腿”等不合理组合时自动重写。
- 不只修截图中的单句，要覆盖所有方案生成和后续换餐回复。

## 2. 免费游客服务边界

### 当前状态

- 已能根据六项信息给出一餐搭配、分量参考和部分替换建议。
- 已有“先试试看、不用一下改变太多”等渐进式引导。
- 但能力边界主要依赖提示词，没有形成稳定、可测试的产品规则。
- 免费游客目前没有精确能量计算，也没有长期档案和饮食事件落库。

### 统一修改目标

免费游客提供：

- 根据就餐场景、口味、预算、忌口、目标和运动情况给出当下饮食建议。
- 提供合理分量、替换方案和渐进改变建议。
- 用户主动反馈饿、撑、不喜欢或实际没有某道菜时，继续即时调整。
- 可以进行当前对话内的轻量提醒和鼓励。

免费游客不提供：

- 宣称后台正在严格控制卡路里。
- 精确基础代谢或每日能量计算。
- 每日饮食持续追踪、阶段计划和自动调整。
- 主动定时推送。
- 经期、运动消耗等长期健康事件追踪。
- 跨设备恢复完整档案。

长期方案使用“估算能量需求并动态调整饮食安排”，不使用“严格控制每一卡路里”这类承诺。

## 统一修改前的处理原则

- 继续人工测试并追加问题。
- 暂不调整 LangGraph 节点、提示词和输出守卫。
- 测试结束后按问题类型拆分：状态识别、产品边界、营养内容、单位校验、排版话术。
- 每项修改都补回归测试，最后再跑完整真实流程。

## 3. 长期方案建档与14天体验开始时间

### 实测问题

用户选择长期方案后，当前话术会直接表示“开启14天免费试用期”，但此时身体数据、经期等长期档案信息可能尚未收集完成，也还没有给出建档后的第一份正式方案。

### 统一修改目标

- 用户选择长期方案时只进入 `long_term_selected` / `onboarding_incomplete`，不立即开始14天计时。
- 第一份通用餐食建议属于体验前的预览方案，不作为长期体验开始时间。
- 两秒后单独询问用户是否方便继续完善长期档案，并提供“现在继续”或“今天晚一点继续”两个选择。
- 用户选择稍后填写时，使用已经确认的简洁话术：

> 好呀，现在没空也没关系～记得今天方便时回来跟我说“继续建档”。完成档案后，我就能正式开始陪你一步一步向目标靠近啦。

- 用户当天回来发送“继续建档”后，从未完成的长期信息继续收集，不能重新走六项基础问询。
- 资料收集完成后，先复述关键档案并让用户确认，再发出建档后的第一份正式长期方案。
- 只有第一份正式长期方案成功发出后，才记录 `trial_started_at`，并按精确时间计算14天。
- 记录 `trial_ends_at` 和结束前一天的 `renewal_reminder_at`。
- 第13天提醒用户是否续订，使用“续订”而非“缴费”；未获得明确确认不得自动扣费。
- 体验未开始、尚未完成档案的用户，不触发续订提醒或费用逻辑。

### 建议状态

- `long_term_selected`
- `onboarding_incomplete`
- `profile_confirmed`
- `trial_active`
- `trial_expired`
- `subscribed`

## 4. 一次输入多项信息时重复确认食堂模式

### 实施状态（2026-08-06）

已完成代码级修复与真实接口验证：清晰字段按用户原文整体接收；同字段确认完成后会从当前项和队列中同时清除；模糊推断与真实改口仍保留确认。

### 实测复现

测试人第一句同时提供“主要在食堂、食堂自选”等多项信息。秘书先询问：

> 你刚说的“自己挑菜”是食堂现在的打饭方式吗？还是只是偏好这样？

用户明确回答“是食堂现在的打饭方式”后，秘书又重复询问：

> 你刚说的“自己挑菜”，是指食堂能自由选菜、不固定套餐那种吗？

### 统一修改目标

- 用户已经明确确认 `cafeteriaMode` 后，立即标记为已确认并移出待确认队列。
- 检查 `pendingConfirmationQueue` 和当轮重新抽取是否同时保存了同一字段。
- 同一字段、同一候选值只允许出现一次确认。
- 补充“一句话提供六项信息与食堂模式”的真实回归测试。

## 5. 分目的自然确认话术库与防重复规则

### 实施状态（2026-08-06）

已完成本轮 P0：确认问题改为按“首次推断/信息改口/菜品口味推断”生成确定性话术；禁用机械开场已加入通用格式检测；模型漏抽的清晰常见表达增加原文证据兜底；首次身份介绍移到统一入口。完整证据见 `test-reports/langgraph-v3-p0-humanized-confirmation-2026-08-06.md`。

补充顺序规则：已有档案用户明确说“我回来啦/我又来了”且同时表达吃多、焦虑等情绪时，消息顺序固定为“欢迎回来 → 情绪支持 → 具体解决办法”。欢迎语由入口节点单独发送，后续回答节点不得重复生成“回来啦”。

### 实测问题

连续确认多个字段时反复出现“诶、哎、你刚说、刚看到”，并多次使用近似句式。即使每句语义正确，连续出现仍像机械问卷；部分问句还擅自加入用户未提到的“最近”。

### 人设与总原则

贴心、干练的专属饮食秘书。按真实确认目的选择句式，不随机替换同义词，也不按照固定顺序机械轮换。用户表达清晰时直接保存，只追问真正存在歧义或会显著影响方案的内容。

### 基础理解

1. 初次理解：我理解的是「___」，对吗？
2. 重要信息复核：再确认一下，「___」是你的实际情况，对吧？
3. 推断校验：这里我是根据你说的内容理解成「___」，有没有理解偏？

### 补充细节

1. 普通细节：这项我记下了，还想补一个小细节：___？
2. 定向了解：关于___，我再多了解一点：___？
3. 影响方案的条件：___会影响后面怎么搭配，我想确认一下：___？

### 区分原因

1. 饮食排斥：是单纯不喜欢这个味道，还是吃了会不舒服？
2. 饮食习惯：这是平时比较固定的习惯，还是偶尔才会这样？
3. 身体状态：平时一直是这种状态，还是这段时间才有变化？

### 自然过渡

1. 好，这项清楚了。接下来了解一下___。
2. 明白啦，我们再看看___。
3. 记下了，接着确认___。
4. 这一项没问题了，最后再了解一下___。

### 硬性执行规则

1. 绝不连续两轮使用同种开场句式；根据确认目的选择话术。
2. 禁止把“诶、哎、你刚说、刚看到”作为默认确认开场。
3. 用户没有提到时间变化时，不能凭空加入“最近”。
4. 用户描述清晰、无歧义时直接保存，不为走流程多问一次。
5. 仅在语义歧义、模型推断、信息冲突或会显著影响方案的关键数据上启动确认。
6. 同一字段、同一候选值最多确认一次。
7. 连续确认多项信息时，根据“初次理解、推断校验、补充细节、关键条件”等真实目的选句；不得为了避免重复而机械轮换或替换近义词。
8. 用户明确回答后，立即从当前待确认项和待确认队列中清除该字段，不能换一种说法再次追问。
9. “记下了”“已保存”等表述只能在信息实际成功写入档案后使用；写入失败时不得制造已经保存的假象。
10. 一句话包含多个清晰字段时优先整体接收，只单独追问真正存在歧义的字段，不能把全部信息拆成逐项确认问卷。

### 回归测试要求

- 一句话同时提供六项信息和食堂模式，清晰字段直接保存。
- 连续确认多个不同目的字段时，开场和句式不重复。
- 用户没有提到时间变化，回复中不出现“最近”。
- 同一食堂模式确认后不会二次追问。
- 档案写入成功后才允许回复“记下了”。

## 6. 身材目标的提前接纳与中途变更（待定，暂不实现）

### 状态与边界

本节只记录未来的对话逻辑方向，尚未完成产品规则定稿。暂不修改 LangGraph 节点、`systemPrompt.js`、回归测试或数据库 SQL，也不影响当前 001–002 批次数据库设计和审核进度（包括冲突裁决闭环的字段级粒度设计）。

### 已确认的方向

1. 用户在秘书正式询问身材目标之前，已经主动、明确表达的目标应当被保留。流程走到该字段时直接采用，不得为了走问卷流程重复询问。
2. 用户在同一天或不超过 3 天的时间窗口内改变主意时，秘书直接接受并更新目标，不追加不必要的质疑或问询。
3. 超过 3 天后改变目标时，未来的对话逻辑需要先判断变更方向：
   - 目标变得更严格或更极端（例如希望更瘦）：不能直接照单全收；先善意提醒，并了解用户的身体适应情况。
   - 目标变得更宽松（例如目标体重从 57 kg 放宽到 60 kg）：先了解改变原因，确认是用户认真考虑后的选择，再更新目标。

### 数据边界

数据库不保存“本次是否应该接受用户改目标”这类对话决策。数据层只需要能表达可审计的客观事实：

- 目标字段何时被确认。
- 目标字段历史上改变过多少次。
- 每次变更前的值、变更后的值和变更时间。

未来对话层可读取这些事实执行时间窗口和严格度判断，但判断规则不下沉为数据库业务逻辑。

### 未决待办

1. 3 天时间窗口的起算点尚未确定：按用户第一次提到目标的时间，还是按秘书正式确认并写入档案的时间。
2. “严格度判断 + 3 天规则”的适用范围尚未确定：是否只适用于目标体重等可数值化目标；“想瘦肚子”“想让线条更明显”等描述性目标是否使用更简单的变更规则。
3. “先问原因、判断用户是否认真考虑过”尚未形成确定性问法、可接受回答标准和节点转移条件，不得直接实现为模糊的模型自由判断。
