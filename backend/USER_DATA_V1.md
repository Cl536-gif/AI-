# 用户身份与长期档案数据契约 v1

## 设计目标

对话层可以持续修改，但长期数据的含义保持稳定。系统不保存“助手说过的一整段话”作为档案，而是保存经过确认的结构化档案和带时间的事实事件。

## 四类数据

### 1. 用户身份 `users`

只保存匿名 `userId`、创建时间、最后活跃时间、时区和语言。身份表不直接存放饮食或健康详情。

游客设备不直接把客户端传来的 `deviceId` 当作 `userId`。身份解析层校验 UUID 后只保存其摘要，并通过 `user_identities` 映射到服务端生成的 `anon:<uuid>`。正式账号未来使用 `acct:<id>`，账号 ID 必须来自服务端认证上下文，不能相信请求正文里的 `userId`。

当前 v1 已完成游客设备到匿名用户的稳定映射，以及经过后端认证的登录账号认领游客档案。正式账号身份只能来自服务端验证后的认证上下文，不能相信请求正文或浏览器本地存储里的 `userId`。合并成功后，设备摘要映射改为指向正式账号；旧匿名用户标记为 `merged` 并锁定写入，但不删除审计记录。系统不保存原始 `deviceId`，合并追溯使用来源匿名用户 ID 和既有设备摘要映射。

合并采用以下规则：

- 正式账号已有档案优先，游客档案只补充空缺字段。
- 双方非空且不同的字段不会自动覆盖，而是写入 `profile_merge_conflicts` 待审；正式档案超过 30 天未更新时只增加时效提示，仍不自动采用游客值。
- 普通历史事件迁移到正式账号，按幂等键或内容指纹去重；迁移和去重动作只保存事件哈希及引用作为审计，不在审计表复制敏感原文。
- 经期历史可以迁移，但状态改为 `restricted_pending_consent`。游客授权不继承，正式账号重新明确授权后才恢复展示和方案使用。
- 相同游客身份再次合并到同一账号返回原合并结果；试图合并到其他账号会被拒绝。

### 2. 当前档案 `user_profiles`

保存当前有效的结构化快照，并带递增版本号。内容包括：

- 身体基础信息：用户明确提供的生理性别计算参数、年龄、身高、当前体重、目标体重、日常活动。
- 饮食基础信息：场景、食堂模式、每餐预算、口味、忌口、目标和运动基线。
- 经期记录状态：是否适用、是否启用；具体日期不放在快照中。

更新档案时不会丢掉旧版本，每次快照同时写入 `profile_revisions`。调用方可以用 `expectedVersion` 防止两个请求相互覆盖。

当前档案的唯一读取入口是 `getProfile(userId)`，它直接读取 `user_profiles`。`profile_revisions` 只用于审计、排查和未来的人工回滚，不参与当前档案的实时反推，避免调用方因历史记录排序或并发写入读到错误版本。

### 3. 长期事件 `user_events`

事件只追加，不直接修改历史：

- `meal`：正餐。
- `snack`：零食或加餐。
- `body_measurement`：体重等测量。
- `exercise`：运动类型、时长和设备估算消耗。
- `menstrual_period_start`：月经开始日期。
- `menstrual_symptom`：食欲、疲劳、腹胀、疼痛等实际变化。
- `check_in`：阶段反馈。
- `plan_interruption`：断联、旅行、生病或计划中断。
- `user_correction`：用户纠正旧记录。

需要纠错时新增事件，并用 `supersedesEventId` 指向旧事件。`idempotencyKey` 用于避免网络重试造成重复记录。

### 4. 授权记录 `user_consents`

长期档案、经期追踪和主动提醒分别记录授权状态。撤回授权通过新增 `revoked` 记录表达，不覆盖曾经发生的授权事实。

授权状态必须读取该用户、该授权类型的最新一条记录。`recordConsent` 只负责保存授权事实；业务层在读取或写入敏感数据前，仍必须检查最新状态，不能把“数据库里存在历史授权”理解成“当前仍可使用”。

### 授权撤回、停止使用与删除

经期日期和症状属于医疗健康类敏感个人信息，处理前应取得单独同意。撤回与删除按以下规则区分：

1. 最新授权变为 `revoked` 后，立即停止新增经期事件，也停止读取历史经期数据用于生成或调整饮食方案。
2. 撤回不否定撤回前已经合法完成的处理，但不构成继续使用历史数据的依据。
3. 若用户提出删除，或处理目的已经实现、保存已无必要，业务层应执行删除；只有法律要求继续保存或技术上暂时难以删除时，才转为仅存储和安全保护，不再用于产品功能。
4. 用户之后重新授权时，不自动恢复使用旧经期数据。若旧数据仍因合法理由存在，必须再次明确询问用户是否愿意继续沿用。

v1 数据层保存不可覆盖的授权轨迹；业务层已经实现撤回后阻断新增敏感事件，并在构建秘书上下文时阻断历史敏感事件读取。用户主动删除后的物理删除或限制处理仍属于后续工作。在删除能力完成前，LangGraph 不得绕过业务层直接读取经期事件。

## 长期服务状态与 14 天体验

长期服务资格与用户档案、授权记录分开保存。`user_service_status` 保存当前状态，`user_service_transitions` 以追加方式保存每次状态变化，便于审计体验从何时开始、何时结束，以及是否经过明确付费确认。

状态顺序如下：

1. `free`：免费科学饮食问答，不持续记录日常事件。
2. `onboarding_incomplete`：用户已选择长期服务，但资料尚未完善。
3. `profile_confirmed`：长期建档所需资料已确认，但体验尚未开始。
4. `trial_active`：完整资料后的第一份正式长期方案已经发出，14 天体验从该时刻精确开始。
5. `trial_expired`：体验已到期，停止新增长期事件。
6. `subscribed`：已收到明确的支付确认，可以继续长期记录。
7. `cancelled`：长期服务已取消。

必须遵守以下计时规则：

- 用户只说“选择长期”时不能启动体验。
- 完成资料收集或确认档案时不能启动体验。
- 收集资料前给出的普通建议或第一版预览方案不能启动体验。
- 只有完整建档后的第一份正式长期方案成功发出，才能写入 `trialStartedAt`、第 13 天的 `renewalReminderAt` 和第 14 天的 `trialEndsAt`。
- 第 13 天只能提醒用户是否继续，不能自动扣费或自动转为 `subscribed`。
- 没有明确的支付确认凭据，不得开通正式订阅。
- 只有 `trial_active` 和 `subscribed` 状态可以持续写入正餐、零食、运动、打卡及计划中断等长期事件。

第 13 天提醒通过 `user_notifications` 待发送队列处理。每次体验使用开始时间生成唯一 `dedupeKey`：重复运行调度任务只会得到同一条提醒，不会重复创建。提醒在外部发送成功后才标记为 `sent`；发送失败时保持 `pending`，允许安全重试。体验已经到期的用户不会再补建续费提醒。

## 单位契约

进入数据层前统一标准化：

- 身高：厘米 `cm`。
- 体重：公斤 `kg`。
- 金额：人民币元。
- 时间：带时区的 ISO 8601 字符串。
- 设备热量：只作为设备估算值写进事件 payload，不直接等量补回饮食。

原始用户表达可以放在事件 payload 的 `rawText` 中用于审计，但不能代替标准字段。

## 能量计算与审计

成人第一版计算引擎只估算维持状态的基础代谢和日常总能量需要，不自动生成减脂热量缺口。计算方法为 FAO/WHO/UNU 报告保留的 Schofield 体重方程估算 BMR，再乘以中国成人身体活动水平 PAL：轻 `1.50`、中 `1.75`、重 `2.00`。宏量营养范围采用 WS/T 578.1—2017：碳水化合物 `50%～65%`、脂肪 `20%～30%`、蛋白质 `10%～15%`，成人膳食纤维 `25～30 g/d`。

计算必须遵守：

- 先把公斤、斤、克、磅、厘米、米和英寸转换为标准单位，再进入公式。
- 用于选择方程的生理性别参数必须由用户明确提供，不能从称呼、目标人群或模型推断。用户选择长期规划后先询问这一项；生理女性继续长期建档，生理男性转为免费科学饮食问答，不进入长期方案或14天试用。
- 当前公式仅支持 18～79 岁成人，且默认非妊娠、非哺乳；超出范围不能套用成人公式。
- 身高和体重组合明显异常时先要求核对单位，不产生能量结果。
- 手表或设备热量只作为参考事件，不直接等量补回饮食。
- 经期阶段不机械增加或扣减固定热量，后续调整以用户实际食欲、疲劳、疼痛、活动与进食反馈为依据。
- 每次计算写入 `energy_calculations`，保存标准化输入、公式 ID 和版本、假设、输出、权威来源与时间，禁止只保存一个无法追溯的卡路里数字。

权威依据：

- FAO/WHO/UNU, *Human energy requirements*：https://www.fao.org/4/y5686e/y5686e.pdf
- 国家卫生健康委员会 WS/T 578.1—2017：https://www.nhc.gov.cn/ewebeditor/uploadfile/2017/10/20171017152901174.pdf

## 阶段饮食计划版本

长期方案保存为 `user_plan_versions`，不是覆盖式的一段文本。每个版本包含阶段目标、天数、关联的能量计算记录、分餐指导、调整规则、上一版本 ID 和本次调整原因。状态变化保存到 `plan_state_transitions`。

计划状态包括：

- `draft`：尚未正式发给用户，不启动体验。
- `active`：当前正在执行，同一用户只能有一个。
- `paused`：因断联、旅行、生病或生活安排变化暂停。
- `superseded`：被新版本替换，保留历史但不再执行。
- `completed`：该阶段已经完成。

必须遵守：

- 免费用户不能建立长期阶段计划。
- 创建草稿和内部计算都不能启动 14 天体验；完整建档后的第一份正式方案成功发出才启动。
- 新版本必须记录调整原因，并可关联上一版本和当时采用的计算记录。
- 用户断联或计划被打乱时暂停当前版本，不追补漏掉的天数，也不通过少吃或加练进行惩罚性补偿。
- 恢复原计划必须得到用户确认；若现实情况已经变化，应建立新版本，而不是暗中改写旧版本。
- 启用新版本时旧活动版本自动变为 `superseded`，确保不会同时执行两套方案。

## 隐私边界

- 经期日期和症状属于时间事件，不放在公开身份字段中。
- 不记录未确认的模型推断为事实。
- 对话线程 ID 不等于用户 ID；同一用户可以有多个线程。
- 当前 SQLite 是本地第一版实现，正式部署时可以迁移到 PostgreSQL/Supabase，但数据契约不变。

## 与 LangGraph 的接入边界

持久化边界已经接入：LangGraph 先输出“档案补丁”或“事件命令”，业务层校验后再调用 `userStore`。LangGraph 节点不能直接拼 SQL，也不能依赖某一句固定话术触发数据库写入。

长期上下文统一由 `buildLongTermContext(userId)` 构建：

- 免费、建档中和体验到期用户只提供基础档案，不提供计划、计算历史或长期事件。
- 体验中或已订阅用户才提供当前活动计划、最新计算记录和限定时间内的近期事件。
- 经期历史必须同时满足长期服务资格和当前有效的经期授权；授权撤回后立即从上下文消失。
- 提供给模型的事件会移除 `rawText` 等非必要审计原文，只保留当前回答所需的结构化信息。
- LangGraph 接入时只能使用该读取器，不能自行组合数据库查询扩大数据范围。

当前 `/api/chat-langgraph` 请求生命周期已经接入：设备身份解析 → 权限化上下文构建 → 图执行 → 基础档案写入 → 服务选择同步 → 长期事件权限检查与写入。历史状态中的 `serviceTier: subscribed` 仅表示用户选择长期路径，业务层只映射为 `onboarding_incomplete`，绝不能据此伪造正式订阅或启动体验。

长期上下文现仅开放给 `answerFollowUp`：只有 `accessMode: long_term` 才会注入，而且会再次压缩为基础档案、当前阶段计划、最新能量估算与最多 5 条近期事件。用户 ID、各类记录 ID、公式来源、审计原文和 `rawText` 不进入模型提示词。免费及尚未完成建档的用户不注入这条消息，保持原有调用结构。回答必须先处理用户本轮问题，不得主动复述整份档案，也不得在用户未询问时主动展示经期或具体热量数字。

阶段方案调整遵循明确的状态边界：单餐换菜、分量反馈、一次零食、一次运动和普通打卡只作为观察事件，不自动改写当前计划，也不创建新版本。已经发生或明确确定的旅行、生病、断联等 `plan_interruption` 事件会暂停当前活动计划并保存原因。恢复原计划必须再次获得用户确认；目标、作息、就餐条件或活动水平出现持续性明显变化时，先向用户说明可能需要新版并征求确认，完整新方案正式交付前不得声称新版已经建立或启用。

新版生成也必须保留计算与版本来源：作息、就餐环境和口味变化可以沿用上一版已审计的能量计算；年龄、身高、体重、活动水平或方程参数变化必须用完整的新输入重新计算并保存新审计记录。健康或疾病状态变化不得自动生成新版，必须先进入风险评估。新版先作为关联 `parentPlanId` 的草稿保存，草稿不改变当前正式计划；完整新版交付后才激活，同时把暂停的旧版标记为 `superseded`。

LangGraph 已为新版请求建立独立的对话状态：只有存在 `pausedPlan` 且用户明确选择按现状重做时才进入。用户可以在一条消息里提供多项持续变化，节点按字段合并并以编号清单复核；确认阶段继续补充时保留旧内容、更新同字段内容。含糊变化只追问具体缺失点，用户明确确认清单后才形成 `confirmedPlanRevisionRequest`，不会提前创建草稿。

变化清单确认后由计算准备节点分流：作息、就餐环境、口味和目标变化直接沿用原计算；计算字段一旦声明发生变化，旧值立即失效，不能拿旧值冒充新值。用户已经在变化说明中给出的新数值直接复用，否则只补问发生变化的字段，再与未变化的已确认输入组合。新输入必须先通过同一能量计算校验；健康状态变化进入 `risk_review_required`，不进入自动新版生成。

计算准备完成后，LangGraph 生成符合 `ProposedPlanSchema` 的结构化新版及清晰的用户回复，并输出带唯一 `commandId` 的 `planRevisionDraftCommand`。业务层必须先完成计算审计、草稿创建、父版本关联和正式启用，任一步失败都不能返回“新版已生效”的回复。命令状态按 `draft_created → delivered` 持久化：同一命令重试时复用原草稿或原已交付计划，不重复建版；失败且仍为暂停上下文时，图会重发原方案并重试交付，成功后下一轮才清除命令和临时状态。新版回复按变化、餐次和观察规则分段，不暴露内部 ID；鸡蛋、鸡腿、水果等离散食物若被错误写成“半拳、一拳”等单位会阻断交付。
