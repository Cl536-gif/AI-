# 002c 长期建档确认证据边界（方案 B 已确认）

## 1. 静态审核结论

当前 `save_current_long_term_profile_fields(...)` 可以验证：

- 当前用户是 active。
- `confirmedFields` 为非空、无重复、只包含 14 个白名单字段。
- `onboardingSessionId` 必填且格式合法。
- 本轮未确认字段不能夹带在专用 RPC 中被修改。
- 确认值从数据库保存后的规范快照提取，不接受另一份可伪造的值。
- 档案、修订和字段确认事实同事务成功或回滚。

但当前 RPC **不能验证**：

- 秘书是否真的把旧值重新展示给用户。
- 用户是否针对该次展示给出了正面回应。
- `onboardingSessionId` 是否真实对应一次长期建档会话；它目前只是格式受限的字符串。

因此，当前版本实质上完全信任后端/LangGraph 已经做完语义判断。任何能以 `diet_app` 调用该 RPC 的普通后端路径，理论上都可以直接声称某些字段已确认。

## 2. 可选边界

### 方案 A：完全信任 LangGraph

- 保留当前 002a 结构。
- 只在应用代码中限制 RPC 调用点，例如仅允许明确确认节点调用。
- 数据库不保存提问与回应的关联证据。

优点是改动小。缺点是数据库无法阻止普通后端调用冒充确认，不完全符合已确认的严格尺度。

### 方案 B：数据库一次性确认请求链（建议）

新增追加/状态受控表 `app.long_term_profile_confirmation_requests`：

| 字段 | 含义 |
| --- | --- |
| `request_id` | 数据库生成的一次性请求 ID |
| `user_id` | 当前用户 |
| `onboarding_session_id` | 后端生成的建档会话键 |
| `prompt_turn_id` | 秘书主动展示待确认值的轮次 ID |
| `presented_fields` | 该次明确摆出的字段与规范值 |
| `prompted_at` | 提问/展示时间 |
| `status` | `pending/consumed/cancelled` |
| `response_turn_id` | 用户正面回应的轮次 ID，消费时写入 |
| `responded_at` | 用户回应时间 |
| `created_at/resolved_at` | 数据库创建与解决时间 |

分两步：

1. 秘书确定要主动摆出旧值时，受信后端调用 `begin_current_long_term_profile_confirmation(...)`，生成 `pending request_id`。
2. 用户在后续轮次正面回应后，调用完成 RPC，必须提供 `request_id + response_turn_id`。

完成 RPC 可由数据库确定性验证：

- 请求属于当前用户和相同 `onboarding_session_id`。
- 请求仍为 `pending`，且只能消费一次。
- `response_turn_id` 非空、不等于 `prompt_turn_id`，并且回应时间不早于提问时间。
- 本次保存的 `confirmedFields` 必须是 `presented_fields` 的子集，且保存后规范值必须与展示值完全一致。
- 本轮未确认字段不能夹带修改。
- 保存档案、追加修订、写入确认事实和消费请求同事务成功。

这可以阻止普通代码路径用一次直接 RPC 调用冒充确认，并留下“摆出了什么—哪一轮回应—最终保存什么”的结构化链路。

同一用户、同一建档会话出现新的不同提问轮次时，旧 `pending` 请求被单向改为 `cancelled`，但原行、展示值、提问轮次、创建时间和解决时间全部保留。相同提问轮次的同参数重试返回原请求；同一轮次携带不同参数则拒绝。完成请求也采用相同原则：响应丢失后的同参数重试返回原档案修订，不重复保存；参数变化则拒绝。

## 3. 数据库仍然无法独立证明的事情

即使采用方案 B，如果 PostgreSQL 不保存完整对话内容、也不对自然语言做语义判断，它仍然需要信任 LangGraph 对“这条用户回答是正面确认”的确定结果。

数据库能够强制的是结构和时序，不是对话语义本身。如果要让数据库完全独立复核语义，就需要把完整提问、用户原文及判定版本也纳入不可变对话审计。这会显著扩大隐私数据范围，不建议为本次档案合并引入。

## 4. 已确认结论

已于 2026-08-18 确认采用方案 B：数据库保存最小化、不含对话原文的一次性确认请求链；LangGraph 只负责判定用户回应是否为正面确认。

该方案新增一张表和起始 RPC，因此局部重新打开 002a、002b 审核。局部审核通过后再继续 002c 其余 RPC 审核。
