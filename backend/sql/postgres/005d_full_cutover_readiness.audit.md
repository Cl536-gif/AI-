# 005d PostgreSQL 全量切换准备审计

审计日期：2026-08-25（Asia/Shanghai）

状态：`NOT READY`。本审计不修改线上 CloudBase 045 SQLite，不导入真实用户数据，不把全量门禁改为通过。

## 1. 已满足的技术基础

1. UserStore 生产端口共有 37 个方法，全部已归类为 `database_ready`，没有未分类、缺表或待改契约方法。
2. PostgreSQL 适配器实现 37/37 方法，只使用参数化查询；004c–004m 已覆盖档案、活动设置、服务状态、能量、计划、提醒、建议、事件、授权、快照和身份合并。
3. 用户事务设置 RLS 用户上下文，并配置 statement、lock 和 idle transaction 超时；回调结束后检查未等待查询并清理连接。
4. 连接池配置有边界、就绪检查验证数据库/最小权限角色/空用户上下文，日志错误经过安全分类。
5. 单实例、单连接池灰度完成真实 HTTP 身份和建议写入，并通过精确清理与独立零残留复核。
6. 默认图持久化协调器已修复启动期缓存 SQLite Store 的问题，真实 PostgreSQL 建议证据通过。
7. 线上已恢复 CloudBase 045 SQLite 稳定路径。

这些证据证明“受控单实例 PostgreSQL 路径可工作”，不等于“可承接全量、多实例、长期生产流量”。

## 2. 当前失败关闭机制

- `tencentPostgresUserStoreCapabilities.js` 将 37 个方法标为 `database_ready`。
- `isTencentPostgresCutoverReady()` 只在每个方法均为 `implemented_and_verified` 时返回 true。
- 当前没有任何方法被提升为该最终状态，因此全量门禁必然返回 false。
- `TENCENT_PG_CUTOVER_MODE=full` 即使带独立确认词，也会抛出 `POSTGRES_FULL_CUTOVER_NOT_READY`。

此处不是能力清单错误，而是刻意保留的发布阻断。不得为了通过测试直接把字符串批量改为 `implemented_and_verified`。

## 3. 全量切换阻塞项

### B1｜LangGraph 会话状态仍是进程内存

`chatLanggraph.js` 使用 `MemorySaver`。同一 thread 落到不同实例或实例重启后，多轮槽位、确认状态和待办流程会丢失。全量生产前必须改用共享持久化 checkpointer，或证明所有请求长期固定到同一不会重启的实例；后者不符合可靠生产要求。

### B2｜全量模式没有连接容量与实例拓扑门禁

单实例灰度强制实例上限 1、连接池上限 1；全量模式目前只检查确认词和布尔 readiness，没有校验 CloudBase 最大实例数、每实例池上限、数据库最大连接数、运维保留连接及总预算。必须建立：

```text
总应用连接上限 = 最大实例数 × 每实例连接池上限
总应用连接上限 + 运维保留连接 <= 数据库安全连接预算
```

声明值还必须与控制台真实配置独立核对，不能只相信环境变量。

### B3｜现有 SQLite 数据去向没有当前证据

早期只读盘点曾确认当时没有正式业务数据，但此后已运行多个 SQLite 稳定修订和真实 HTTP。全量切换前需要重新执行只读数据盘点，并明确选择：空库新启动、停机迁移，或受控导入与逐表对账。当前没有运行中双写，也不应临时引入未经验证的双写。

### B4｜一次图持久化跨多个独立事务

档案、建议、服务状态、事件、计划调整和计划交付依次调用多个 UserStore 方法，每个 PostgreSQL 方法拥有自己的事务。中途失败可能留下前半段已提交、后半段未执行的状态。已有部分幂等键，但尚缺真实 HTTP 级故障注入、重放和最终一致性证明。

### B5｜多实例/重启端到端验证缺失

现有 005b–005c 只允许单实例。尚未证明同一匿名身份、同一 thread、多轮采集、重复请求和计划命令在两个应用实例及滚动重启后保持一致。

### B6｜运行监控与自动回滚信号不足

已有安全错误日志，但没有连接池 `total/idle/waiting` 指标、借用等待分位数、事务超时率、RLS/身份失败率、HTTP 副作用失败率的阈值与告警。没有这些信号就无法安全判断扩大流量或触发回滚。

### B7｜回滚制品与数据回滚演练不足

005c 回滚时旧稳定修订在控制台不可直接选择，只能新建 SQLite 修订。全量切换前必须固定可复用的稳定提交/镜像、环境变量快照和一键回滚步骤，并演练“应用回滚但 PostgreSQL 已产生新写入”时的数据处理边界。

### B8｜备份恢复与传输安全尚未签核

仓库中没有当前 PostgreSQL 备份恢复演练证据，也没有对生产连接采用 `verify-full` 或私网明文连接的风险签核。全量真实用户数据进入前，必须证明可恢复点、恢复时间、备份保留和网络/证书边界。

## 4. 允许提升全量门禁前的退出标准

1. 将 LangGraph checkpointer 迁移为跨实例共享持久化实现，完成重启和双实例多轮测试。
2. 为 full 模式新增最大实例、池上限、数据库安全预算和控制台实值复核门禁。
3. 重新盘点 SQLite 数据，形成逐表数量、身份映射、抽样哈希和迁移后对账方案；若确认为零，也需留存只读证据。
4. 对图持久化每个阶段做故障注入，证明重放不重复、不会越权、能收敛到一致状态。
5. 建立连接池、事务、readiness、HTTP 副作用和身份错误的指标、阈值与告警。
6. 固定 SQLite 回滚制品并完成滚动发布/回滚演练。
7. 完成 PostgreSQL 备份恢复演练和传输安全签核。
8. 形成方法级证据矩阵；只有每个方法及上述运行门槛均有可追溯证据时，才能把能力状态提升为 `implemented_and_verified`。
9. 在独立预生产环境完成多实例小流量观察窗口；生产全量切换需要另一次明确授权。

## 5. 005d 结论

- 当前可以继续：SQLite 稳定运行；PostgreSQL 单实例、固定测试身份的受控验证。
- 当前禁止：多实例 PostgreSQL、真实用户数据迁移、全量流量切换、把 readiness 直接改为 true。
- 下一实现批次建议：005e 共享 LangGraph checkpointer 与跨重启/双实例状态一致性；它是全量切换的首要架构阻塞。
